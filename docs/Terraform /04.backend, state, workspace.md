# 04. backend, state, workspace

# 1. backend 
> **backend**란? 
> - terraform 은 영구적인 state data 파일을 계속 관리해야 함 
> - `backend = state data` 파일이 저장되는 위치 

## 1-1. backend 종류 
- local : disk(HDD, SDD), 기본 설정 
- remote 
    - Terraform Cloud 
    - Object storage 
        - state file은 보통 git에 저장하지 않으므로, versioning을 통해 백업 용도로 활용 가능
        ```hcl
        versioning_configuration {
          status = "Enabled"
        }
        ```
    - k8s secret
    - postgres DB 
    - Gitlab
- remote 문제점 
    - 민감정보(key, pw) 분리가 필요 
    - 민감정보는 환경 변수로 분리하여 backend-config 옵션을 통해서 사용하는 것을 권장 -> 현업에서는 backend-config 사용도 쉽지 않음 
    - locking을 위해서 `Dynamo DB` 등 NoSQL에 저장하기도 함 

- `*.tfstate` 파일이 생성됨
- `*.tfstate.backup` 백업용 파일 생성됨

```bash
❯ terraform state list
module.vpc_list["dev"].aws_subnet.private_subnet_1
module.vpc_list["dev"].aws_subnet.public_subnet_1[0]
module.vpc_list["dev"].aws_vpc.default
module.vpc_list["prd"].aws_subnet.private_subnet_1
module.vpc_list["prd"].aws_vpc.default
```

## 1-2. backend 설정 예제
```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
  ## backend 설정
  backend "s3" {
    ## hard-coding 필요, terraform block 에서는 변수 사용이 불가능하다. 
    ## 가장 먼저 loading 되는 block 이므로
    bucket  = "tf-backend-hansgun" 
    key     = "terraform.tfstate"
    region  = "ap-northeast-2"
  }
}
```
- 다중 계정으로 terraform을 운영할 경우 s3를 backend로 쓸 수 밖에 없음 
- S3 에 대한 보안 (최소 암호화) 설정은 필요하다. 

# 2. 상태 관리 
- terraform 은 인프라나 설정에 대해서 무조건 state 로 저장함 
- state 는 기본적으로 terraform.tfstate 라는 로컬 파일에 저장됨 
    - backend 가 remote 인 경우에는 환경마다 다름 
- state는 terraform 으로 선언된 설정과 실제 인프라 객체를 매핑하기 위해 존재함 
- 즉, state가 없으면 terraform 으로 인프라 관리를 할 수 없음 

> versioning, 암호화 등 으로 history 보호와 내용 관리가 필요하다. 

- **state 파일이 저장된 위치의 성능**에 따라 terraform 성능에 영향이 발생함 
    - `plan/apply` 실행 시 매번 로컬에 저장된 state와 API로 호출된 값을 비교 
    - `-refresh=false` 옵션을 통해서 로컬에 저장된 state만으로 비교 가능 
    - remote backend 사용시 환경에 따라서 추가 지연 발생 가능

- 하나의 terraform module 을 여러명이서 관리할 때는 state 파일을 공유해야함 
    - backend를 remote 로 사용 
- S3 와 같은 파일 시스템을 사용할 경우에는 동시에 동일한 state 파일에 접근 시 충돌이 발생함 
- state 파일이 손상되거나 인프라 설정의 정합성이 맞지 않을 수 있음 
  → `concurrency` control이 필요함 
  → 인프라 설정의 정합성이 맞지 않을 경우 더 심각함
- state locking 하기 위해서 dynamoDB 등 추가 설정이 필요함

- 여러 개의 환경을 관리할 때 locking이 발생하여 수정을 못하는 경우가 발생
    - ex) A가 운영환경에 배포하는 동안 locking이 발생하며, B는 개발환경에 테스트가 불가능한 경우 
    - **환경별로 상태 파일 분리가 필요**
        1. 디렉토리를 분리(환경별로 root module 생성)
        2. workspace 분리

# 3. 리소스 강제 교체(`taint/untaint`)

## 3-1. `terraform taint / untaint `
- 강제로 리소스를 재생성하는 방법
- Elastic IP 재생성, 비정상적인 리소스 처리를 위해 사용 
    - blacklist로 신규 IP가 필요할 경우 
    - `terraform apply` 도중 hang 발생하는 경우 등
- ex
    ```bash
    $ terraform apply -replace="aws_instance.test[0]" 
    ```

# 4. workspace 
- 환경에 따라서 state를 관리하고자 할 때 사용 가능 
- workspace 별로 state가 별도로 저장됨 
- 일부 backend 만 multiple workspace 지원 
    - k8s
    - local 
    - postgres
    - remote(terraform cloud)
    - S3 
    - 다만, 일부 backend 는 기능 사용에 제한이 있으므로 세부 내용 확인 필요함 

- backend 설정
  ```hcl 
  terraform {
    required_providers {
      aws = {
        source  = "hashicorp/aws"
        version = "~> 5.0"
      }
    }

    backend "s3" {
      # backend S3 사용
      bucket = "tf-backend-hansgun"
      key    = "terraform.tfstate"
      region = "ap-northeast-2"
    }
  }

  esource "aws_s3_bucket" "tf_backend" {
    bucket = "tf-backend-hansgun"

    versioning { ### versioning deprecated
      enabled = true
    }

    tags = {
      Name = "tf_backend"
    }

  }
  resource "aws_s3_bucket_acl" "tf_backend_acl" {
    # bucket 명이 static 하므로 하나의 bucket 사용하는 것이 권장됨 
    # backend-config를 통해서 동적으로 할당 가능하지만 
    bucket = aws_s3_bucket.tf_backend.id
    acl    = "private"
  }
  ```

## 4-2. workspace 설정 
- root module 에서 접근하는 방법 

  ```hcl
  ### root module 내에서 접근
  module "vpc_list" {
    source = "./hans_vpc"
    env    = terraform.workspace  ## terraform 변수화 
  }
  ```
- `tfi -migstate` 를 통해 init 진행 
  ```bash
  $ `tfi -migrate-state`
  Initializing the backend...
  Initializing modules...
  Initializing provider plugins...
  - Reusing previous version of hashicorp/aws from the dependency lock file
  - Using previously-installed hashicorp/aws v5.82.2

  Terraform has been successfully initialized!

  any changes that are required for your infrastructure. All Terraform commands
  ```

- workspace로 `apply` 할 경우, state 저장 backend에 workspace 별로 폴더가 생성되며, 하위에 state 파일이 저장된다. 
  ```bash
  $ `tree terraform.tfstate.d` 
  terraform.tfstate.d
  ├── dev
  └── prd
  ```

### 4-2-1. workspace prefix 변경 
- default 로 `env:` prefix가 설정되는데, window의 경우 `:` 기호를 폴더 이름으로 사용할 수 없다. 
- 이 경우 backend 설정에서 변경 가능하다. 
  ```hcl 
  ## root module 
  terraform {
    required_providers {
      aws = {
        source  = "hashicorp/aws"
        version = "~> 5.0"
      }
    }

    backend "s3" {
      # backend S3 사용하는 경우
      bucket               = "tf-backend-hansgun"
      key                  = "terraform.tfstate"
      region               = "ap-northeast-2"
      workspace_key_prefix = "temp" #### workspace prefix 설정하는 구문 
    }
  }
  ```
