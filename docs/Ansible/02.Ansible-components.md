# 02. Ansible components 

## 1. 구성 요소 
### 1-1. Inventory 
- 작업 대상 서버와 변수 정보를 저장 
- `ini`, `yaml` 파일로 설정 
→ 최근에는 `ini` 보다는 `yaml` 형채로 많이 사용 

#### 1-1-1. Inventory 구성 요소 
- all 
    - 모든 호스트(서버) 정보
- children 
    - 그룹별 호스트 정보 
    - 일반적으로 작업 단위 별로 설정 
- api.example.com[1:10]
    - 1~10번까지의 호스트 설정 
- 직접 IP 설정도 가능 
- ex
    ```yaml 
    all:
        hosts:
            a.test.com:
            b.test.com:
            c.test.com: 
            api.example.com[1:10]:
            10.0.0.5:
        
        children: 
            web:
                hosts:
                    a.test.com:
                    b.test.com:
            db:
                hosts:
                    c.example.com:
                    d.example.com:
    ```
### 1-2. module 
- 단일 명령어나 수행할 작업 
    - 단일 명령어 : `cp, apt, wget` 
- 기본 bullet-in module 도 제공 : [메뉴얼 페이지](https://docs.ansible.com/ansible/latest/collections/ansible/builtin/command_module.html#command-module)
- **단, 윈도우는 별도 모듈 사용** 
→ 스크립트 실행 환경이므로 굳이 bullet-in 이 없더라도 동일 내용 작성 가능하나, 편의성 증대.. 
- 주요 문법(요소)
    - becom : root 권한 
    - register: 결과값 저장 
    - update_cache : apt update 

### 1-3. handler 
- ansible이 지원하는 조건부 형식
    - 조건에 맞을때 handler를 실행
- task에서 notify를 이용하여 handler의 name을 매개변수로 전달하여 사용 
- 일반적으로 모든 task가 실행되고 handler가 실행됨
- notify를 여러번 받아도 handler는 1번만 실행됨
- playbook에 다수의 handler를 포함하면 notify 순서가 아닌 handler 섹션에 정의된 순서대로 실행됨

## 2. 실행 
### 2-1. ad-hoc command
- playbook 을 작성하지 않고 직접 ansible module을 호출해서 실행하는 방식 
- 재사용이 필요 없는 명령어를 어러 호스트에서 실행 가능 
    ```bash
    $ ansible [pattern] -m [module] -a "[module options]"

    # test group 에 있는 모든 서버를 10개 단위로 재부팅 시 
    $ ansible test -a "/sin/retoot" -f 10 ## `-f` 의 default 값은 5

    ## bullet-in module 을 통해 모든 서버에 특정 파일 권한 수정 
    $ ansible test -m ansible.builtin.file -a "dest=/tmp/foo/bbb.txt mode=644"

    # test group에 있는 모든 서버에 특정버전 패키시 설치 
    $ ansible test -m ansible.builtin.yum -a "name=acme-1.5 state=present"
    ```

### 2-2. playbook 
- 호스트와 task를 연결하는 역할 
- playbook에서 task를 지정해서 작업 진행 가능 
    ```bahs
    ansible-playbook playbook.yml -f 10 
    ansible-playbook playbook.yml -i staging -i production 
    ```
- task를 묶어서 Role 로 만들어서 반복 사용 가능 
- roles 폴더 내부에 정의해두면 자동으로 읽어 옮 
    - task : 작업 내용
    - handler : 핸들러 
    - template : role 템플릿 
    - files : 정적파일 
    - vars : 변수 
    - defaults : 기본 변수이며, vars에게 overwrited 될 수 있는 변수 
    - meta : 작성자, 라이센스 같은 메타 정보, validation 
    - library : custom module 
- ex : [ansible manual-roles](https://docs.ansible.com/ansible/latest/playbook_guide/playbooks_reuse_roles.html)
    ```bash 
    roles/
    common/               # this hierarchy represents a "role"
        tasks/            #
            main.yml      #  <-- tasks file can include smaller files if warranted
        handlers/         #
            main.yml      #  <-- handlers file
        templates/        #  <-- files for use with the template resource
            ntp.conf.j2   #  <------- templates end in .j2
        files/            #
            bar.txt       #  <-- files for use with the copy resource
            foo.sh        #  <-- script files for use with the script resource
        vars/             #
            main.yml      #  <-- variables associated with this role
        defaults/         #
            main.yml      #  <-- default lower priority variables for this role
        meta/             #
            main.yml      #  <-- role dependencies
        library/          # roles can also include custom modules
        module_utils/     # roles can also include custom module_utils
        lookup_plugins/   # or other types of plugins, like lookup in this case

    webtier/              # same kind of structure as "common" was above, done for the webtier role
    monitoring/           # ""
    fooapp/               # ""
    ```
