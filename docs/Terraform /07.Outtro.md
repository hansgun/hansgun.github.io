# 07.Outro

## 1. 운영 전략
- 개인(소규모 프로제트) : local 
- 협업이 필요하거나 팀 단위 관리가 필요한 경우 
    - Terraform Cluod, Gitlab 
        - 동시성 처리 문제
        - 보안 문제 
- 다중 환경/계정 사용 시 = 다중 workspace 
    - S3(+ dynamoDB)
    - NAS, PostgrSQL 등

### 1-1. backend - 단일 bucket? 
- backend 설정에서는 표현식이나 변수 사용이 불가능하므로 단일 버킷 사용 
    - `terraform cli` 옵션 중 `-backend-config` 를 통해서 값을 바꿀 수 있음 : 외부 파일의 값을 가져올 수 있음 
        - 권장 되는 사항은 아님
- 다중계정으로 S3 사용시 **assume role을 통해서 다른 계정에 접근** 
    - 계정을 여러 개 사용하는 경우 key를 여러 개 관리해야 함 
    - anywhere role로 임시 키를 관리하는 경우
- S3 cross account 설정을 통해서 사용할 경우, 운영계정의 access key 관리를 위한 정책이 필요 
- 되도록 운영계정은 role base로 운영

### 1-2. 환경 분리, 다중 계정 관리 : `workspace`
- 다중 계정과 환경을 한 번에 관리? 
    - ex : project_a_dev / project_b_prd ... : workspace로 관리가 유리 
    - terraform은 동일한 환경을 재사용할 때 유리함 
- 테스트하기 위해서 개발 환경이 있는데, 개발/운영환경이 달라진다면...? <br/>
→ workspace를 쓰기보단 sub module롭 분리하여 사용

### 1-3. 디렉터리 구조 
1. 파일은 최대한 분리 
    - 리소스 타입, 서비스 단위
2. 큰 서비스(애플리케이션)은 sub module 
    - module화의 장점 : 개념적으로 분리하기 쉬워짐(label name을 짧게 쓸 수 있다.) 
3. sub module이 너무 커지면 프로젝트로 분리 
    - module 간에 output으로 참조하던 부분은 data로 처리 
    - **sub module state import/export 는 공식적인 지원 하지 않음**
4. 환경(dev/prd)별로 sub module로 나누는 방식은 권장하지 않음 
    - 물론, 워크로드에 따라서 오히려 좋을 수 있음

### 1-4. module 
1. 되도록이면 provider나 커뮤니티에서 지원해주는 것을 사용 
2. 다만 OS나 프로세서(intel, arm)에 의존성이 있는지는 확인이 필요 
    - 갑작스럽게 deprecated 되거나 M1 맥북에서 안되는 일부 플러그인 존재 
3. 자체적으로 private registry를 운영하여 필요한 외부 module은 fork 받아서 운영하는 것도 하나의 방법
    - 공식적으로 registry 장애 발생 시 대응 가능 
    - 회사 내 module 공유 
    - 필요시 직접 bugfix 하여 사용 가능 
4. modle version은 fix해서 사용
    - version이 올라가면서 기본값이 달라지거나 버그가 발생할 수 있음
